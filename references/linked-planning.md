# 相互参照で運用するプロジェクト管理

## 基本構造

文書を「入口・現在地」「計画・判断・作業」「成果物・根拠」に分け、必要な関係を通常のMarkdownリンクで結ぶ。全件を読み込むことや、専用アプリのバックリンク機能を前提にしない。

| 役割 | 答える質問 | 更新する契機 |
|---|---|---|
| 入口・ルーティング | どこから読む？ 何をどこへ書く？ | 構成・担当範囲が変わる |
| 現在地 | 何ができていて、何が不確か？ | 到達点・制約・検証状態が変わる |
| 計画・判断・TODO | なぜ行う？ 次に何をする？ | 優先度・方針・作業状態が変わる |
| 正本・成果物・証拠 | 何を採用し、何を作り、どう確かめた？ | 内容・実装・検証が変わる |
| 履歴・旧版 | 何が変わった？ 前の案はどう扱う？ | 置換・保留・重要な転換が起きる |

役割の分離とリンクの組合せがフレームワークの中心。フォルダの番号、W1–W5、研究固有の名前は移植しない。

## 継続案件での配置

```text
README.md                 全体の入口
AGENTS.md                 依頼別ルーティングと更新規則
docs/STATUS.md            現在地。既存の相当文書を優先
master-plan/
  README.md               この管理層の役割
  00-index.md             現在の計画・優先TODO・保留への入口
  records/                PLANとDECなどの独立した記録
  todos/                  完了条件を持つ作業
```

初期計画を `records/` に作成する。判断記録とTODOは独立して追跡する内容がある時点で作る。`inbox/`、`log/`、`archive/`、作業領域別サブフォルダは必要時に追加する。初期化時に仮の決定や未依頼の作業を捏造しない。

仕様・本文・ソース・原資料は各分野の適切な場所へ置き、この管理層からリンクする。管理層には成果物の全文を複製しない。既存の課題管理サービスが正本ならTODOはそのURLへ接続する。

## リンクの契約

各リンクには「親計画」「採用判断」「依存する作業」「検証証拠」などの意味を付ける。「関連」だけの羅列にしない。

| 関係 | 順方向 | 戻り道 |
|---|---|---|
| 案内 | 索引 → 現行計画・優先TODO | 計画 → 索引 |
| 作業分解 | 計画 → 独立TODO | TODO → 親計画 |
| 採用理由 | 計画 → 判断 | 判断 → 影響する計画・正本 |
| 実行・検証 | TODO → 成果物・検証証拠 | 計画側からTODO経由で辿れること。ソース全体への逆リンクは不要 |
| 置換 | 新記録 → 旧記録 | 旧記録 → 後継記録 |

依存関係は `AはBの完了後に着手` と方向・条件を明記する。対称な関連と混同しない。循環する依存が見つかったら着手可能な単位へ分けるか、未解決として扱う。

通常の相対Markdownリンクを使い、リンク表示は短い内容名またはIDにする。IDだけでクリック先のない参照にしない。全ファイル同士の相互リンクや、引用元すべてへの逆リンクは不要。入口から到達できない現行記録、親に戻れないTODOを残さない。

## IDと状態

独立記録には `PLAN-YYYYMMDD-NNN`、`DEC-YYYYMMDD-NNN`、`TODO-YYYYMMDD-NNN` を付ける。同じ種別・日付の既存IDを検索し、未使用番号を選ぶ。名称や保存場所が変わってもIDは保持する。日付は実際の記録日とし、コピー元の日付を残さない。

必須のfrontmatterは `id`、`type`、`status`、`updated`。タグ・優先度・作成日などは使う場合だけ追加する。関係は本文のリンクを正本とし、同じ関係を `related_ids` 等へ機械的に二重入力しない。既存プロジェクトで両方を使っている場合は勝手に削除せず整合を確認する。

| 記録 | 状態 | 条件 |
|---|---|---|
| 計画・判断 | draft / active / superseded | 提案、採用、後継による置換を区別 |
| TODO | open / ready / in-progress | 未完了、着手条件が明確、実行中 |
| TODO | done | 完了条件を満たす成果物と確認結果がある |
| TODO | paused / cancelled | 保留は再開条件、取消は不要になった理由を残す |
| 受領メモ | unprocessed / processed | 処理済みには反映先を示す。作業完了とは別 |

採用判断の `active` は技術的正しさや検証済みを意味しない。アーカイブへの移動は作業の完了でも取消でもない。

## 変更を関連文書へ反映する

1. **依頼を受ける。** 今実行する依頼か、将来のTODO登録かを区別する。未処理原文を保持する必要があればinboxへ置き、処理後に反映先を示す。
2. **計画につなぐ。** 既存作業を検索して重複を避ける。独立した完了条件や依存関係を持つ作業だけTODO化する。親計画と相互リンクする。
3. **判断を残す。** 後続の作業に影響する選択について、採用内容・根拠・退けた選択肢・見直し条件を記す。許可されていない判断はdraftにする。
4. **実行結果を反映する。** 成果物の正本を更新し、TODOに実際の検証と残作業を記す。完了条件を満たした場合だけdoneにする。索引は短い表示とリンク、現在地は到達点の要約に留める。
5. **方針変更を処理する。** 影響する依存先をリンクから確認する。旧記録をsupersededにして新旧を結び、不要になった作業は理由付きで保留・取消にする。重要な変更だけ履歴へ残す。

生成するAGENTS.mdへ、この手順と対象パスを記す。一度構成を作るだけでなく、作業のたびに関係と状態が維持されるようにする。

## 再現できたかの確認

リンク切れ検査だけでなく、次の質問を実際の文書を辿って答える。

1. 「次の作業は？」— 入口→索引→優先TODO→着手条件・完了条件。
2. 「なぜこれをする？」— TODO→親計画→採用判断→根拠。
3. 「何を直す？」— TODO→更新対象の正本。提案先と作成済み成果物を区別できる。
4. 「本当に終わった？」— doneのTODO→成果物→対象版の検証証拠。
5. 「方針を変えたら？」— 判断→影響する計画・TODO、旧記録↔後継。保留作業の再開条件が残る。

該当する記録がまだない質問には「未決定」「未検証」と答えられればよい。見かけの完全性のために記録を作らない。移動時はIDとパスの全参照を検索し、リンク・アンカー・索引を修正する。
