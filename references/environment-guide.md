# 人間とAIの協業環境を作るガイド

## 目標

新しく参加した人やエージェントが、入口から「何を作るか」「何が決まったか」「どこを直すか」「何が未完了か」に辿れること。会話履歴を読まなければ進められない状態を減らす。

機能的Q-learning研究プロジェクトの管理方法から、正本の指定、段階的な参照、現在と旧案の分離、検証状態の明示を一般化した。研究固有の手法・数値・ファイル階層は継承しない。

## 1. 規模に合わせた構成

継続的なプロジェクトの標準は、[相互参照フレームワーク](linked-planning.md)に従う `master-plan/` 型の管理層とする。計画・判断・TODOを文書間リンクで辿れる形式を優先する。[記録の雛形](record-formats.md)から実際に必要な記録だけを具体化する。

次は小規模な案件の縮小例。継続案件では `docs/PLAN.md` の役割を `master-plan/00-index.md` と個別記録へ分ける。両方を並行する計画台帳にしない。既存構成があれば、その名前と配置を優先する。

| ファイル | 一元管理する情報 | 含めない情報 |
|---|---|---|
| `README.md` | 目的、成果物、使い始め方、主要文書への入口 | 詳細な進捗台帳、仕様の全文 |
| `AGENTS.md` | 読む順序、依頼別の参照・更新先、検証方法、作業境界 | 毎日変わる進捗や長い経緯 |
| `docs/STATUS.md` | 現在の到達点、採用方針の短い要約、検証証拠、未解決事項 | TODOの複製、過去ログ全文 |
| `docs/PLAN.md` | 優先順、作業状態、完了条件、判断理由 | 成果物・仕様そのものの別コピー |

小さな案件ではSTATUSとPLANを1つにまとめる。仕様や本文は実作業に合わせて追加し、READMEから導線を張る。コードを持たないプロジェクトに `src/` や `tests/` を作る必要はない。

最初に埋める情報は、会話・既存成果物から確認できた事実。たとえば「目的：家計の支出を可視化」「現在：雛形のみ」「検証：未実施」「次の作業：CSV読込、完了条件：サンプル3件が表示される」。不明な予算、納期、技術選定を決定済みと書かない。

## 2. 依頼から読む場所・書く場所へ振り分ける

AGENTS.mdの開始手順は短くする。READMEと現在地を読み、依頼に該当する文書へ進む。全ファイルやアーカイブを毎回読む手順にしない。

次の表を対象プロジェクトの実在パスで具体化する。未作成のパスはリンクにせず「必要時に作成」と明示する。1つの依頼が複数の種類にまたがる場合は、必要な行を組み合わせる。

| ユーザーの依頼 | まず読む | 主に更新する | 完了の確認 |
|---|---|---|---|
| 「何ができた？」「次は？」 | 現在地、計画 | 状態が変わった場合のみ該当文書 | 記録と成果物・検証証拠の整合 |
| 「方針を決めたい」「仕様を変えて」 | 仕様の正本、判断理由 | 仕様、判断記録、影響する計画 | 影響箇所と未実装範囲の明示 |
| 「作って」「直して」 | 対象の仕様、実装入口、近傍の規約 | 実装・本文などの成果物、関連する状態 | 小さなテスト、ビルド、目視など |
| 「調べて」「比較して」「レビューして」 | 対象成果物、原資料 | 依頼された報告・コメント | 出典と推論、未確認事項の区別 |
| 「前の案は？」「引き継いで」 | 現在地、必要な旧案・判断のみ | 依頼に必要な引継ぎ情報 | 現在と過去、完了と保留の区別 |

説明・診断・レビューは、その依頼だけでは実装変更の許可にならない。既に変更が許可されている場合はその範囲で進める。人間に判断が必要な事項には、選択肢・推奨・影響を添える。可逆的なファイル配置や通常の検証はエージェントが進める。

## 3. 正本と証拠を分ける

同じ情報に2つの更新先を作らない。「要件は仕様書」「実装はソース」「次の作業は計画」のように役割を明示する。複数の文書が矛盾していたら、日時だけで正しさを決めず、決定記録と実物を確認する。解消できない矛盾は未解決事項に残す。

状態の記載では、次の違いを保持する。

- **採用済み**：方針として選んだ。実装や検証は別。
- **実装・執筆済み**：成果物が存在する。正しさの保証は別。
- **検証済み**：対象、方法、結果、必要なら版・実行日を特定できる。
- **未検証・保留**：未確認や停止の理由、再開条件がある。完了ではない。
- **置換済み**：後継の正本がある。旧文書には後継へのリンクを付ける。

凍結結果・原資料・公開版は作成時の前提と結びつける。新しい仕様に変わっても、以前の結果を新仕様の検証として使わない。追加解析は別の出力先へ置く。

## 4. 日々の運用をAGENTS.mdへ残す

各プロジェクトのAGENTS.mdには、具体的なパスとともに次のルールを記す。

1. 作業開始時に入口・現在地・対象の正本を読む。既存変更を確認する。
2. 変更は該当の正本へ行う。検討メモを増やして本体の更新を放置しない。
3. 実際の成果物に合った最小検証を行い、実行できなかった確認は明記する。確認済みのコマンドは実行場所も記す。
4. 到達点・制約・次の作業が変われば状態と計画を同期する。進捗が変わらない編集で日報を量産しない。
5. ファイルを移動したら参照を検索して更新する。構成の変更時は入口とルーティングも更新する。

報告は、できたことを先に、変更先と検証結果を短く示す。未完了なら次の具体的な作業を1つ示す。長い会話ログをそのまま保存するのではなく、後続作業に必要な判断と根拠を残す。

## 5. 成長に合わせて増やす

| 起きている問題 | 追加するもの | 作らなくてよい段階 |
|---|---|---|
| 仕様の説明がREADMEから溢れる | 仕様・設計の正本 | 概要だけで作業できる |
| 採用理由を何度も調べ直す | 判断記録。日付、理由、代替案、影響 | 計画内の短い記録で足りる |
| 調査メモが探せない | 調査索引と原資料へのリンク | メモが少なく直接辿れる |
| 旧案を現行と誤認する | アーカイブ、後継へのリンク | 旧版を保存する必要がない |
| 特有の手順を繰り返す | プロジェクト固有スキル | AGENTS.mdの数行で足りる |

研究なら方法章・実験・文献、アプリなら仕様・ソース・テスト、制作なら企画・原稿・素材が成果物の正本になる。フォルダ名より役割を揃える。外部の課題管理や文書サービスが既に正本なら、そのリンクとローカル文書の責務を明示し、二重管理を避ける。

## 6. 引渡し時の確認

1. READMEから現在地・計画・成果物に辿れるか。リンク先と相対パスは正しいか。
2. 「仕様変更」「実装・執筆」「状況確認」の依頼で、読む場所・書く場所・確認方法を説明できるか。
3. 仕様・実装・検証の状態は証拠と一致するか。未実施を完了と書いていないか。
4. 既存内容を消していないか。同じスキルを再適用したとき、既存の役割を再利用できるか。
5. 本来の依頼も進んだか。管理用の空ファイルや未置換テンプレートだけを成果にしていないか。

## この端末での呼び出しと自動適用

このスキルは個人用の `~/.agents/skills/project-foundation/` に置く。Berdでは個人スキルとして発見でき、Codexでもユーザースコープの検索先である。スキル名を指定する場合は「project-foundationを使って、このプロジェクトの協業環境を整えて」でよい。

Codexの `~/.codex/AGENTS.md` には、新規プロジェクトの作成時にこのスキルを読む共通ルールを置く。ルールは新しいセッションで読み込まれる。別の `CODEX_HOME`、上書き用指示、別端末・別エージェント環境では読み込み条件を確認する。

自動適用とは、新規作成の依頼を受けたエージェントが環境整備を併せて行うこと。フォルダを作っただけで動く監視処理は含まない。Berdでのスキル検出と、各実行エンジンによる自動選択は別であり、後者の実動作は新しいセッションで確認する。

仕様確認（2026-10-05）：[Codexの共通指示](https://learn.chatgpt.com/docs/agent-configuration/agents-md)、[ユーザースコープのスキル](https://learn.chatgpt.com/docs/build-skills)。Berdの検出は `berdctl skill list --json` で確認できる。
